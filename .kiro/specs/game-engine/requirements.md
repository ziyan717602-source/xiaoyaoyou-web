# Requirements: game-engine

## 项目描述

将 PSDGamepkg 的核心引擎（XI.cs、XIG.cs、XIR.cs，共 8,000+ 行代码）翻译为 TypeScript，实现事件驱动的 G-Loop 系统和回合状态机。

**当前状态**:
- 核心数据模型已就绪（core-models 完成）
- 无事件系统和回合管理
- 参考源码：XI.cs（2,165 行）、XIG.cs（3,125 行）、XIR.cs（1,130 行）

**期望结果**:
- G-Loop 事件系统可独立运行
- 回合状态机可执行完整回合流程
- 技能注册表（sk02）可正确构建
- 选将系统（SelectHero）可执行

## 范围

**包含**:
- XIG.cs 翻译（事件系统）
- XIR.cs 翻译（回合状态机）
- XI.cs 翻译（游戏初始化、选将）
- Artiad 模块（动作解析器）

**不包含**:
- 卡牌效果实现（card-effects 模块）
- 网络通信（network-server 模块）
- UI 组件（client-ui 模块）

**边界**:
- src/shared/game/engine/event-bus.ts — 事件总线
- src/shared/game/engine/g-loop.ts — G-Loop 核心
- src/shared/game/engine/round.ts — 回合状态机
- src/shared/game/engine/xi.ts — 游戏初始化
- src/shared/game/engine/artiad/ — 动作解析器

## 需求

### 1. 事件总线系统

#### 1.1 事件总线核心

- 系统必须实现 `EventBus` 类，作为事件驱动架构的核心组件
- 系统必须支持 `on(event, handler)` 注册事件监听器
- 系统必须支持 `off(event, handler)` 移除事件监听器
- 系统必须支持 `emit(event, data)` 触发事件并传递数据
- 系统必须支持事件优先级排序，高优先级处理器先执行
- 系统必须支持事件取消（`stopPropagation`），阻止后续处理器执行
- 系统必须支持一次性监听器（`once`），触发后自动移除

#### 1.2 技能注册表（sk02）

- 系统必须实现 `SkillRegistry` 类，管理所有技能的事件注册
- 系统必须支持从 Skill/Tux/Monster/NPC/Evenement 对象提取事件注册信息
- 系统必须支持按 occur 字符串匹配事件类型（如 `G0OH`、`G1OH` 等）
- 系统必须支持按 priority 排序多个同类型处理器
- 系统必须支持 once 标志，确保一次性技能只触发一次
- 系统必须支持 hind 标志，控制处理器是否阻止后续执行
- 系统必须支持 lock 标志，控制处理器是否锁定（不可被其他效果移除）
- 系统必须支持 linked 标志，判断技能是否与其他技能联动
- 系统必须支持 demiurgic 标志，标记创造者技能（如祝福技能）

#### 1.3 事件消息类型

- 系统必须实现 `GMessage` 接口，作为所有 G-Loop 消息的基础类型
- 系统必须实现 `InnerGMessage` 类，表示内部消息（无需网络传输）
- 系统必须实现 `SimpleGMessage` 类，表示简单消息（含发送者、接收者、消息内容）
- 系统必须实现 `SimpleGMessage100` 类，表示扩展消息（含额外参数）
- 系统必须支持消息的序列化和反序列化，保持与原版字符串协议兼容
- 系统必须支持消息的克隆和修改，用于消息链处理

#### 1.4 事件分发机制

- 系统必须支持按消息类型（G0OH 等）查找匹配的处理器
- 系统必须支持按玩家队伍过滤处理器（红方/蓝方/全体）
- 系统必须支持按优先级排序处理器执行顺序
- 系统必须支持处理器执行结果的收集和传递
- 系统必须支持处理器执行的异常捕获和日志记录

### 2. G-Loop 核心系统

#### 2.1 G-Loop 主循环

- 系统必须实现 `GLoop` 类，管理游戏主循环
- 系统必须支持消息队列管理，按优先级处理消息
- 系统必须支持消息的入队和出队操作
- 系统必须支持主循环的启动、暂停和停止
- 系统必须支持消息处理的异步执行（async/await）
- 系统必须支持消息处理的超时控制

#### 2.2 消息处理流程

- 系统必须支持消息的接收和解析
- 系统必须支持消息的预处理（如参数校验、格式转换）
- 系统必须支持消息的分发（按消息类型路由到对应处理器）
- 系统必须支持消息的后处理（如状态更新、日志记录）
- 系统必须支持消息处理结果的回调通知

#### 2.3 消息类型定义

- 系统必须支持 G0OH（全体消息）类型
- 系统必须支持 G1OH（红方消息）类型
- 系统必须支持 G2OH（蓝方消息）类型
- 系统必须支持 G0OT（全体目标消息）类型
- 系统必须支持 G1OT（红方目标消息）类型
- 系统必须支持 G2OT（蓝方目标消息）类型
- 系统必须支持 G0OP（全体操作消息）类型
- 系统必须支持 G1OP（红方操作消息）类型
- 系统必须支持 G2OP（蓝方操作消息）类型
- 系统必须支持其他消息类型（如 G0OO、G1OO、G2OO 等）

#### 2.4 消息参数处理

- 系统必须支持消息参数的解析和类型转换
- 系统必须支持消息参数的默认值处理
- 系统必须支持消息参数的范围校验
- 系统必须支持消息参数的序列化和反序列化

### 3. 回合状态机

#### 3.1 回合阶段定义

- 系统必须实现 `RoundPhase` 枚举，定义所有回合阶段
- 系统必须支持 `ROUND_START` 阶段（回合开始）
- 系统必须支持 `DRAW_PHASE` 阶段（摸牌阶段）
- 系统必须支持 `MAIN_PHASE` 阶段（主要阶段）
- 系统必须支持 `BATTLE_PHASE` 阶段（战斗阶段）
- 系统必须支持 `END_PHASE` 阶段（结束阶段）
- 系统必须支持 `ROUND_END` 阶段（回合结束）
- 系统必须支持阶段之间的转换规则

#### 3.2 回合状态管理

- 系统必须实现 `RoundManager` 类，管理回合状态
- 系统必须支持当前阶段的获取和设置
- 系统必须支持阶段转换的触发和验证
- 系统必须支持阶段转换前的检查（如条件是否满足）
- 系统必须支持阶段转换后的处理（如状态更新、事件触发）
- 系统必须支持阶段转换的回滚（如取消操作）

#### 3.3 回合流程控制

- 系统必须支持 `RunRound` 方法，执行完整回合流程
- 系统必须支持回合开始时的初始化（如重置状态、触发回合开始事件）
- 系统必须支持摸牌阶段的执行（如从牌堆摸牌、触发摸牌事件）
- 系统必须支持主要阶段的执行（如出牌、使用技能）
- 系统必须支持战斗阶段的执行（如伤害计算、战斗事件）
- 系统必须支持结束阶段的执行（如状态清理、触发结束事件）
- 系统必须支持回合结束时的处理（如分数计算、下一回合准备）

#### 3.4 回合事件触发

- 系统必须支持回合开始事件（`ROUND_START`）
- 系统必须支持摸牌事件（`DRAW_CARD`）
- 系统必须支持出牌事件（`PLAY_CARD`）
- 系统必须支持战斗事件（`BATTLE_START`、`BATTLE_END`）
- 系统必须支持回合结束事件（`ROUND_END`）
- 系统必须支持阶段转换事件（`PHASE_CHANGE`）

### 4. 游戏初始化系统

#### 4.1 游戏初始化流程

- 系统必须实现 `XI` 类，作为游戏引擎的入口
- 系统必须支持 `Run()` 方法，启动游戏主循环
- 系统必须支持游戏状态的初始化（如创建 Board、Player、LibGroup）
- 系统必须支持牌堆的初始化（如从 JSON 数据加载卡牌）
- 系统必须支持玩家的初始化（如创建 Player 对象、分配队伍）
- 系统必须支持技能注册表的初始化（如从 Skill/Tux/Monster 提取事件）

#### 4.2 MappingSksp 映射

- 系统必须实现 `MappingSksp()` 方法，构建技能注册表
- 系统必须支持从所有 Tux 对象提取事件注册信息
- 系统必须支持从所有 Monster 对象提取事件注册信息
- 系统必须支持从所有 NPC 对象提取事件注册信息
- 系统必须支持从所有 Evenement 对象提取事件注册信息
- 系统必须支持从所有 Skill/Bless 对象提取事件注册信息
- 系统必须支持注册信息的去重和合并

#### 4.3 游戏配置

- 系统必须支持游戏模式配置（如标准模式、扩展模式）
- 系统必须支持玩家数量配置（如 2 人、4 人、6 人）
- 系统必须支持卡牌包配置（如标准包、扩展包）
- 系统必须支持随机种子配置（如固定种子、随机种子）

### 5. 选将系统

#### 5.1 选将流程

- 系统必须实现 `SelectHero` 类，管理选将流程
- 系统必须支持选将阶段的初始化（如随机分配可选英雄）
- 系统必须支持玩家选择英雄（如 pick、switch 操作）
- 系统必须支持英雄交换（如 switchAt、switchTo 操作）
- 系统必须支持选将结果的验证（如检查选择是否合法）
- 系统必须支持选将完成的确认（如锁定选择）

#### 5.2 Casting 集成

- 系统必须支持 CastingPick 模式（个人选将）
- 系统必须支持 CastingTable 模式（公共选将）
- 系统必须支持 CastingPublic 模式（公开选将）
- 系统必须支持 CastingCongress 模式（会议选将）
- 系统必须支持不同模式之间的切换
- 系统必须支持选将消息的序列化和反序列化

#### 5.3 选将事件

- 系统必须支持选将开始事件（`SELECT_START`）
- 系统必须支持英雄选择事件（`HERO_PICK`）
- 系统必须支持英雄交换事件（`HERO_SWITCH`）
- 系统必须支持选将完成事件（`SELECT_END`）
- 系统必须支持选将超时处理

### 6. Artiad 动作解析器

#### 6.1 动作解析器核心

- 系统必须实现 `Artiad` 模块，作为动作解析器
- 系统必须支持动作字符串的解析（如 `G0OH,1,2,3,1`）
- 系统必须支持动作参数的提取和类型转换
- 系统必须支持动作的执行（如调用对应的处理器）
- 系统必须支持动作结果的收集和返回

#### 6.2 动作类型定义

- 系统必须支持卡牌效果动作（如 `JP06Action`）
- 系统必须支持技能效果动作（如 `SK01Action`）
- 系统必须支持怪物效果动作（如 `MO01Action`）
- 系统必须支持 NPC 效果动作（如 `NJ01Action`）
- 系统必须支持事件效果动作（如 `EV01Action`）
- 系统必须支持操作动作（如 `OP01Action`）

#### 6.3 动作执行环境

- 系统必须支持动作执行的上下文（如当前玩家、目标玩家、消息数据）
- 系统必须支持动作执行的异常处理（如无效动作、条件不满足）
- 系统必须支持动作执行的日志记录
- 系统必须支持动作执行的调试信息

### 7. 单元测试

- 系统必须为 EventBus 编写单元测试，覆盖事件注册、触发、取消、优先级
- 系统必须为 SkillRegistry 编写单元测试，覆盖注册、查找、匹配
- 系统必须为 GMessage 类型编写单元测试，覆盖序列化、反序列化
- 系统必须为 GLoop 编写单元测试，覆盖消息队列、主循环
- 系统必须为 RoundManager 编写单元测试，覆盖阶段转换、流程控制
- 系统必须为 XI 编写单元测试，覆盖初始化、配置
- 系统必须为 SelectHero 编写单元测试，覆盖选将流程、Casting 集成
- 系统必须为 Artiad 编写单元测试，覆盖动作解析、执行
