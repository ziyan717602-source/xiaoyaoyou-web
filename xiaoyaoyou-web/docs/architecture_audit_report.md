# 仙剑·逍遥游 Web版 - 项目审计与架构优化建议文档

> **编制日期：** 2026-05-31
> **目标项目：** xiaoyaoyou-web (C# WPF 向 Web 架构迁移项目)
> **审计范围：** 核心引擎、网络通信协议、AI调度机制、前端组件与 UX 交互体验

基于对现有代码库设计、迁移历史文档（如 `dev-log.md`, `wpf-vs-web-comparison.md` 等）及最新一轮联机测试反馈的深入追踪与分析，本项目目前已基本完成了原版 C# 引擎效果层（100%卡牌、技能）的硬核翻译。然而，在将“桌面单机同步架构”强制转换为“现代 Web 异步多人联机架构”的过程中，系统在底层状态机调度、网络通信范式以及用户交互设计上，暴露出严重的脱节。

以下将从三大核心方向为您提供深度的项目审计剖析及具体可行的重构指导方案。

---

## 一、核心引擎实现（Engine & Logic）

### 1.1 现状与病灶剖析
1.  **引擎缺乏异步状态挂起机制（阻塞与等待缺失）**
    原版 C# `RunRound` 采用了经典的桌面端长流程串行设计，通过 UI 线程阻塞直接等待用户输入。Web 版虽然将回合划分为 28 个阶段（Phase），但引擎调度本质上仍是在同步轮询或盲目触发事件。在需要等待人类玩家决策的环节（如 `ZD` 战牌阶段、`ZC` 技能触发阶段），如果未能强制将引擎挂起（Pause/Suspend），就会导致事件“呼啸而过”，造成玩家反馈的“没有使用战牌和混战的机会”。
2.  **阵营判定逻辑错位（Targeting Flaws）**
    在 1v1、2v2、3v3 模式中，战斗支援（Z1）与妨碍（ZW）的目标选取规则对阵营高度敏感。目前代码在触发妨碍者选择时，往往错误地将判定权交给了触发者（当前回合玩家），或简单通过硬编码的 `opponent` 变量选取，未考虑团队中存在多名队员的寻址路由逻辑，导致乱点鸳鸯谱。
3.  **系统级流转死角（如牌库无重洗机制）**
    卡牌引擎设计中缺失了最基础的生命周期防崩机制。游戏仅挂载了 56 张初始手牌至 `tuxPile`。根据桌游常识，当牌堆耗尽时，理应触发“弃牌堆重洗加入牌堆”的逻辑。目前由于 `lib.draw()` 方法缺少临界监控，一旦 56 张抽空，整个引擎的物资链即刻崩溃断裂。

### 1.2 架构优化建议
*   **引擎状态机重构：引入 Async/Await 与 Generator 模型**
    彻底摒弃基于全量同步的流转。将 `round.ts` 的主阶段派发器（Phase Dispatcher）改写为异步阻塞结构。例如在 `ZD`（战牌）阶段：
    ```typescript
    // 伪代码示例
    async function runZDPhase(combatContext) {
        broadcastPhaseState('ZD_COMBAT');
        // 将引擎强制挂起，直到等待到合法的玩家出牌 Promise 解析，或触发超时机制
        const playerAction = await waitForInput({ 
            validTypes: ['combat_card', 'hero_skill'], 
            timeoutMs: 15000 
        });
        
        if (playerAction) {
            applyAction(playerAction);
            await runZDPhase(combatContext); // 递归或循环处理下一张战牌
        }
    }
    ```
*   **抽离并建立统一的“团队路由（Team Routing）”层**
    在 `Board` 或 `GameSession` 状态管理中，植入强类型的枚举标识 `enum Faction { TeamA, TeamB }`。彻底封装所有对象的索引与获取方法，诸如 `getOpposingTeam(uid)`、`getAllTeammates(uid)`。对于任何牵涉多人的阶段（特别是 ZW 妨碍阶段），引擎下发的交互授权（Input Request）必须仅针对 `getOpposingTeam` 的玩家列表。
*   **植入防崩卡牌生命周期事件**
    在核心的抽牌接口中硬性封装洗牌重置逻辑。
    ```typescript
    function drawTux(count) {
        if (tuxPile.length < count) {
            tuxPile.push(...shuffle(discardPile));
            discardPile = [];
        }
        return tuxPile.splice(0, count);
    }
    ```

## 二、服务器通信与 AI 调度（Architecture & Netcode）

### 2.1 现状与病灶剖析
1.  **AI 的“极速运算”破坏了时间与动画维度**
    由于 AI 逻辑（RuleAI / GreedyAI）以函数的形态内嵌在 Node.js 服务端，运算延迟通常小于 5 毫秒。当轮到 AI 出牌或进行打怪、翻事件等动作时，服务端在一个事件循环内就跑完了成堆的逻辑，并把海量状态瞬间倾泻给前端。人类玩家在视觉上只看到卡牌飞速流失，毫无响应时间，这也是为何会产生“服务器高速消耗怪物不等待我”的客诉。
2.  **交互耦合过深（格式化字符串的遗毒）**
    目前的通信依然基于对 C# 格式字符串（如 `T1(p1p2)` 或 `/Q`）的拼凑。虽然前端写了复杂的 `format-parser.ts` 勉强应对，但这违背了前后端分离“服务端只负责下发状态和合法动作”的原则，导致扩展任何新的交互方式都异常困难。

### 2.2 架构优化建议
*   **AI 的“虚拟客户端化（Virtual Client Isolation）”**
    在架构上，应将 AI 与主引擎彻底解耦。设计一套虚拟客户端接入层：让 AI 以“伪造 WebSocket 连接”的身份加入房间。引擎并不关心对方是 AI 还是人类，只管发送 `input_request`，由外部的 AI 调度器负责解析并调用对等的提交接口。
*   **实施强流控：人工延迟（Artificial Delay）与时间轴同步**
    必须在服务端的全局广播体系中引入强有力的时间轴管控：
    *   **思考模拟器**：在接收到 AI 的指令时，服务端强制 `await sleep(1000)` 1秒，在此期间广播给全服一个“XX正在思考/正在打出XX”的预留动画状态。
    *   **抢断读条机制**：面对需要全服响应的瞬时打断动作（如任意玩家使用冰心诀），必须实装一个带有倒计时的“抢断窗口（Interrupt Window）”（如 5 秒）。在 5 秒内，若有人响应则终止倒计时，否则时间走完继续结算下一个引擎事件。
*   **通信协议全面重构为强类型 JSON Payload**
    废除晦涩难懂的拼接字符串，所有向客户端的索要操作一律改为语义化的描述，使前端能够进行自由的数据渲染。
    ```json
    {
      "type": "input_request",
      "phase": "SKILL_CARD_PHASE",
      "requiredAction": "SELECT_TARGET",
      "validTargets": ["player_3", "player_4"],
      "optional": true
    }
    ```

## 三、前端实现与 UI/UX 体验（Frontend & UX）

### 3.1 现状与病灶剖析
1.  **强加给玩家的“操作割裂感”**
    前端因为拘泥于旧版命令行的解析器，在“使用技牌”这样高频的操作上，玩家无法直观地从下方的“手牌区”点击选中自己想打的牌，反而是由系统从中央凭空弹出一个单独的“确认窗口”。这种设计不仅割裂，而且完全背离了现代卡牌游戏的操作直觉。
2.  **主次视觉元素失焦**
    事件卡、怪物卡翻出时，本应是游戏最具悬念和张力的时刻。而当前版本仅仅用粗糙的文本日志（附带一个小滚动条图标）来通报，未能激活精美的图鉴资源（`eve_*.png` 等）；新加入的技能面板虽然实现了，但很可能因为缺乏高亮反馈而被忽视。

### 3.2 架构优化建议（对标现代卡牌桌游范式）
*   **重建所见即所得的“点控式”交互流（Point-and-Click UX）**
    彻底取消常态化出牌时烦人的中间弹窗。
    *   **智能手牌映射**：当阶段要求打出手牌时，前端根据接收到的 `valid_actions`，直接将对应的组件（`HandArea`）激活。合法的卡牌会浮起（悬停动效）并出现金色流光描边。
    *   **连贯的两步走操作**：玩家点击手牌（选中） $\rightarrow$ 画面其他不相关元素变暗，合法目标（头像或怪物）高亮 $\rightarrow$ 玩家点击目标 $\rightarrow$ 触发一道飞牌动画并向后端发出动作请求。
*   **重塑战场视觉中心区（Battle Center）**
    *   **剧场模式弹窗**：在 `EV`（事件阶段）或 `ZM`（翻取怪物）阶段，提取卡片原画大图，直接在屏幕正中央实施放大的 3D 卡牌翻转（Flip）入场动画。悬停展示 2-3 秒，并配上震动或粒子特效，随后缩小吸附至战场区域或宠物槽。
*   **悬浮组件（Tooltip）与信息收纳**
    桌游的文本量极其庞大。不要试图在面板上常驻展示所有属性和效果。应当为所有卡牌、Buff、状态图标统一封装高阶的 `Tooltip` 悬浮层（移动端支持长按呼出）。例如详细技能说明、怪物失败惩罚等，只需悬浮便可优雅查阅。
*   **构建“防呆”与二次确认安全网**
    为了弥补网络延迟和操作手误，必须在关键节点实装“二次确认”。例如：界面右下角设计显著的“跳过阶段/结束回合”操作按钮；当玩家在战牌阶段手握“金蝉脱壳”却准备空过时，触发一次轻巧的 Toast 提醒以规避误触。

---

**总而言之**，目前的 Web 版本已经证明了 C# 核心效果翻译在 Node.js 环境下的可行性（全用例 Pass）。下一步的架构重心，应当坚决地从“代码逻辑的堆砌”向“调度控制流的管控”与“人机交互直觉的现代化重塑”转型。这份蓝图将助推系统真正进化为一款具备商业潜力的网络桌游应用。
